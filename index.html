Course guide · Agentic development for React

How an AI agent builds a React feature, and where people stay in charge

This guide covers a pipeline built with Claude Code for a React 19 + Vite + TypeScript app. The agent plans, designs, specs, codes, tests and opens pull requests. Tools check its work after every edit, and a person approves at exactly two gates. Each section below covers one part: the commands, the agents, the hooks, the loops and the gates.

The one principle: automation does not remove the human gate. It moves it to the pull request. Everything before the PR can be automated heavily because nothing reaches main until CI is green and a human approves.
  • Human: intent, decisions, merges
  • Agent: planning and execution
  • Machine: hooks, CI, deterministic checks
  • Gate: a hard stop for a human decision
  • File / artifact
6slash commands, the human’s only interface
2human gates that are never skipped
3hooks: before a command, after an edit, at turn end
2 + 2subagents + GitHub Actions agents
400reviewable lines, maximum per PR
3failed attempts, then the agent stops and asks

Ownership

Who owns what

The pipeline divides work into three roles. Most mistakes in agentic development happen when these roles blur: the agent makes product decisions, or a person rereads code that a tool could have checked.

Human owns intent + decisions

  • Describes the feature (plan mode → features.md)
  • Edits the design on claude.ai
  • Answers Gate 1: “yes” / “yes except 2”
  • Reviews the PR + preview and merges (Gate 2)
  • Adds labels, branch protection, CODEOWNERS
  • Agrees (or not) to new CLAUDE.md rules

Agent owns execution

  • Writes requirements, designs screens, writes specs
  • Sends short gate briefs that ask for decisions
  • Implements tasks.md with tests
  • Fixes whatever hooks/CI report, up to 3 attempts
  • Opens the PR with the full template
  • Archives specs, proposes rules

Machine owns enforcement

  • Hooks: format, lint, typecheck on every edit
  • Hooks: related tests + react-doctor at turn end
  • Guard hook: blocks merges / force pushes
  • CI: typecheck, lint, tests, e2e, bundle, doctor
  • CI: PR size ≤ 400, bot-approval detection
  • Branch protection: the final backstop

What this costs the reviewer each week: about 5 min per Gate 1 brief, 10–20 min per Gate 2 PR (preview click-through plus the “Review carefully” lines), and a quick look each morning at autopilot’s “Question:” and “Split needed:” issues.

Interface

The six slash commands

The human uses only these six commands. Everything else (the feature-pipeline skill, the openspec-* skills and the subagents) is internal: the agent calls them itself.

/start

Once per project. Turns a copy of the template into your project. It never scaffolds a new app and asks before every step, one decision at a time, with a recommended default.

  1. Check it’s a fresh copy: the package name is still the template’s and the example feature exists.
  2. Name the project: package.json, the CLAUDE.md title, the README.
  3. Styling + UI library: Tailwind (default) / CSS Modules / Sass / CSS-in-JS, and shadcn/ui (default) / MUI / Chakra / AntD / Radix / none. Conflicts are flagged. Choices are recorded in architecture.md with who decided and when.
  4. Remove the example items feature, leaving a placeholder home page and keeping the test harness green.
  5. First intent: 1–3 features in features.md, the API situation (OpenAPI / informal / frontend-first) and hosting.
  6. Design: a Claude Design Design System (tokens) + a canvas with one page per feature. Tokens are written into the @theme block.
  7. Commit + PR on chore/project-setup, with a “Why this is N lines” breakdown because the setup PR is always large.
  8. GitHub checklist for the human: install the GitHub app, CODEOWNERS, branch protection, the large-pr-approved label, and optionally AUTOPILOT_ENABLED.

/feature <idea>

Plans one change: intent → design → spec. It writes no application code. It moves quickly on routine, reversible steps, and confirms before installs, pushes or PRs.

  1. Define: behaviour, states, edge cases and open questions go into features.md. If an API is involved, the contract is settled first.
  2. Design check: an existing page is reused; with no page, one is designed (an artboard per state per width in the existing look); a change with no UI skips design.
  3. Spec: the openspec-propose skill. Over 400 lines → split. tasks.md ends with approved: <pending>.
  4. Hand over and STOP, with a short summary: risk, size, design link, open decisions with defaults, and “edit the design, then run /build <change>”.

Given an existing change name, it only shows that change’s status and the next command.

/build <change-name>

Gate 1 → code → verify → PR. This is where most of the automation runs.

  1. Re-read the live design. Diff it against design.md / tasks.md. Behaviour differences update the spec.
  2. GATE 1 brief (skipped only if a human’s approved: line already exists, for example from a merged spec PR). Waits for an explicit “yes”.
  3. Snapshot the approved page into design/ (artboards, canvas.json, tokens.json) and sync tokens.
  4. Implement on feat/<change> with openspec-apply-change, task by task, with tests. react-reviewer runs after each chunk. Decisions and dead ends are logged in notes.md.
  5. Verify: npm run check + npm run test:e2e (axe) + screenshots vs artboards. Three failed attempts → stop.
  6. Ship + GATE 2: confirm, push, open the PR with every template section filled. STOP. Never merge.

Resumable: after /clear, running /build again sees the approved line, reads notes.md and skips to the first unticked task.

/sync-ui [feature]

Brings the code up to date with design edits made after a feature shipped.

  1. Diff the live Design System + canvas against design/. Only pages already built count.
  2. Classify each difference: visual (colour, spacing, copy, token value) or behaviour (a new field, screen or flow).
  3. Behaviour changes → openspec-propose → “run /build for these”. They are not coded here.
  4. Visual changes, after a “yes” → a small low-risk change ui-sync-<date>, whose approval line records that human “yes”, on branch chore/ui-sync-<date>.
  5. Verify, then PR → Gate 2, then /finish ui-sync-<date>.

/finish <change-name>

After a human merges. Closes the loop so the spec matches what shipped.

  1. Check it’s merged: pull the default branch. If the code isn’t there, stop.
  2. Archive with openspec-archive-change, which syncs the delta specs into openspec/specs/ (the living spec).
  3. Mark it shipped in features.md.
  4. Bookkeeping PR on chore/archive-<change>. Never pushes to the default branch.
  5. Learn: if a human made the same correction twice at the gates, propose a one-line CLAUDE.md rule.

/fix <bug>

A lighter lane for bugs in behaviour that is already specified and shipped. The failing test is the spec, so there is no Gate 1, but Gate 2 still applies. Full flowchart in The /fix lane.

Reproduce → branch fix/<slug> → RED test → GREEN minimal fix → add the missing spec scenario if there was a gap → verify → PR → stop.

Life of one change

Every piece of work is an OpenSpec change: a folder in openspec/changes/<name>/. One change = one branch = one PR. The state is written in the files. The last line of tasks.md shows whether a human approved it.

Blue loops are normal iteration. Red is a failure sending work back. Dashed lines are the two side entrances: /fix for bugs, and /sync-ui for design edits after release.

What lives in a change folder

File Written by Holds
proposal.md agent “Risk tier:” line, what & why, Open questions (each with a default), Non-goals, depends on:, new deps with justification
specs/<capability>/spec.md agent Delta spec: requirements + scenarios this change adds or modifies
design.md agent Which artboards (<slug>/<State>.dc.html) it implements + canvas link
tasks.md agent → human First line “Estimated reviewable lines: n”. Tasks ordered contract → logic → UI → wiring → e2e, each with a test task. Last line: approved: <pending>, which only a human replaces

screenshots/ agent <State>-<width>.png from the visual self-check

Detail

Phase by phase

Phase 0: one-time setup

Create the repo with “Use this template”, then npm ci && npx playwright install chromium and run /start. The human does the GitHub work: /install-github-app (API key secret), real CODEOWNERS, branch protection (require CI incl. approvals + PR size, 1 review, Code Owner review), preview deploys, and the large-pr-approved label. Autopilot stays off until the AUTOPILOT_ENABLED=true variable is set.

Phase 1: Define human-led
  • Vague request → discuss in plan mode first. No code.
  • features.md: user-facing behaviour, states (Default / Loading / Empty / Error), edge cases, open questions.
  • architecture.md: styling + UI library, design tokens, API contract source, design links.
  • Contract first. OpenAPI exists → generate RTK Query with npm run gen:api (or hand-write if the spec is messy). Informal (Postman, sample JSON) → Zod schemas. No API yet → write Zod first, mock with MSW, build against the mock.
  • These two files are the inputs to OpenSpec. Nobody keeps a second spec by hand.
Phase 2: Design agent + human edits

One Claude Design canvas per project, one page per feature, one artboard per state per width (default mobile 390 + desktop 1280). The copy is real, from features.md, never lorem ipsum. Designs are accessible as drawn: real buttons, labelled inputs, contrast ≥ 4.5:1. Open decisions sit on the canvas as orange sticky notes. The agent always rereads the live canvas and never builds from memory.

Phase 3: Spec + Gate 1 agent → gate

openspec-propose writes the change folder under the rules in openspec/config.yaml. Size it before the gate: if it will go over 400 reviewable lines, split it into ordered, independently shippable changes (1. contract: Zod + endpoints + MSW, 2. UI: components + tests, 3. wiring: route + e2e), each marked depends on:. Then the Gate 1 brief (see gates).

Phase 4: Implement loop agent ⇄ machine
  • Fresh context: in a long conversation, ask the human to /clear and then re-run /build. The agent resumes from notes.md.
  • Snapshot the design into design/, then sync token changes into the styling layer.
  • openspec-apply-change refuses to start while tasks.md says approved: <pending>.
  • One task at a time. A task is ticked only when its test passes. Files go where the fixed folder structure puts them.
  • Fixed stack: RTK Query for server state, Zustand for UI state, React Hook Form + Zod for forms, MSW for mocks. Responses are validated with Zod in transformResponse.
  • A decision the spec doesn’t settle → stop and ask (with a default). If it is minor and reversible → pick the default and log it in notes.md.
  • After each chunk of work → the react-reviewer subagent, then fix what it reports.
Phase 5: Verify (definition of done) machine 
npm run check      # typecheck + lint + format:check + test:coverage + react-doctor
npm run build      # when adding deps or pages: enforces the bundle budget
npm run test:e2e   # when a user flow changes: Playwright + axe

Then the visual self-check: Playwright screenshots of every state at every width (states driven by MSW overrides), compared with the artboards, at most 3 rounds. Anything left over is listed under “Differences from the design” in the PR.

Phase 6: Ship + Gate 2 agent → gate

Size check with git diff --numstat origin/HEAD...HEAD. The PR body is written to .git/PR_BODY.md, then gh pr create --body-file. If gh isn’t signed in, the agent gives the human a compare link and the body file path instead. CI runs, a preview URL appears, and the agent stops. The agent answers each review comment, and if it disagrees it says why once and lets the human decide.

Phase 7: Finish + learn

/finish archives the change into the living specs and marks it shipped. Corrections that happened twice become proposed one-line CLAUDE.md rules, added only if the human agrees. This is how the system improves over time.

Human in the loop

The two human gates

A gate is a hard stop: the agent cannot continue until a person decides. Gates only work if they fit into a real person’s day, so each one asks for decisions, not reading. A good gate message fits on one screen and can be answered with “yes”, “yes except 2” or a short correction.

Gate 1 Design + tasks.md, before any code

The cheapest place to fix wrong intent, a wrong look, or a PR that will be too big. 

Gate 1 — add-item   Risk: medium   ~220 reviewable lines
Builds: a form to add an item to the list
Design: <canvas link> → page "add-item" (6 screens)
Your design edits since /feature: button label
Decisions I need (my default in brackets):
  1. Max name length? [80 chars]
  2. Keep form open after save? [no, close]
New dependencies: none
Reply "yes" to build, or tell me what to change.

Gate 2 PR + preview, before merge

The human clicks through the preview (not just the diff) and reads the lines marked risky. 

PR #42 — add-item   Risk: medium
Read carefully:
  src/features/items/schema.ts:L4-20  (contract)
  src/features/items/api.ts:L12-30    (cache tags)
Decisions I made without asking:
  - Empty-name error copy: "Name is required"
  - Trim whitespace before save
Preview: https://…vercel.app
I will not merge. After merge: /finish add-item

Approval has to be written down

tasks.md ends with approved: <pending>. Only an explicit human approval turns it into approved: Ana, 2026-09-29. Silence, “looks interesting” or a question do not count. The agent writes that line only after the person says yes, and never on its own. Four separate things protect this rule:

  1. Written rule in CLAUDE.md, the pipeline skill and openspec/config.yaml.
  2. Skill refusal: openspec-apply-change won’t start on <pending>. Autopilot only picks changes with a human’s line.
  3. CI approvals job: fails any PR where a bot or an autopilot/* branch adds an approved: line, or a bot-authored commit touches one.
  4. Async option: a spec-only PR routed by CODEOWNERS. The reviewer adds the line in their review, so a merged spec counts as an approved spec.

Risk tiers: attention scales with risk

Tier Examples Human involvement
low copy, styling, a test, a small isolated component Gate 2 only; a skim is fine
medium new feature UI, state logic, a new dependency Gate 1 + Gate 2 with a preview click-through
high contract / schema, auth, money, data deletion, CI Gate 1 + Gate 2 + a second reviewer

When the agent must stop and ask (never guess)

The spec / features.md doesn’t settle a product or UX behaviour: copy, empty/error states, edge cases.

The change touches the API contract: a Zod schema, an endpoint, a response shape.

It wants a new dependency, or to change architecture.md, CLAUDE.md, CI or hooks.

It would delete or rewrite code outside the change’s scope.

The same check fails 3 times and it doesn’t know why.

The format is always one concrete question plus a recommended answer, so the human can just reply “yes”.

While waiting at a gate, the agent does not start the next step. It says what it’s waiting for and what the human needs to decide, in one or two lines.

Diagram 3

Self-correction: loops inside loops

An agent is useful when it gets fast, automatic feedback on its work and fixes problems before a person sees them. This pipeline has five loops nested inside each other. The inner loops are fast and cheap. The outer loops are slower and involve people.

5 · Review loop Gate 2 comments → agent fixes → push · hours
4 · CI loop quality · size · approvals red → fix → push · minutes
3 · Done-gate loop check + e2e + screenshots, max 3 attempts
2 · Turn loop Stop hook: related tests + doctor · ~1 min
1 · Edit loop post-edit: prettier + eslint + tsc · seconds
Agent writes code

Loops 1 + 2 in detail: one agent turn

Exit code 2 is the key: Claude Code sends the hook’s stderr back to the model, so the fix happens in the same turn. Exit 1 would only show it to the human. The Stop hook checks stop_hook_active so it pushes back only once, which stops an endless loop.

Rules that keep loops from running away

3 strikes

The same failure after 3 honest attempts → stop, explain what was tried and what is probably wrong.

Never weaken a check

Never disable a test, lint rule or hook to get green. Never lower coverage floors or the bundle budget.

Bounded budgets

The Stop hook has a 180 s timeout. GitHub agents are capped by --max-turns (40 / 80) and timeout-minutes (30 / 45).

Scoped checks

vitest related runs only the tests touching changed files. react-doctor --scope changed ignores older issues.

Diagram 4

Hooks in depth

Hooks are shell scripts that Claude Code (the harness, not the model) runs at fixed points in the agent’s loop. They are configured in .claude/settings.json. The model cannot skip them. It only sees what they print. This is the difference between asking for a rule in a prompt and enforcing it with a tool.

One /build turn: a blocked push, a type error fixed through post-edit, and a clean Stop check.

PreToolUse · guard-bash.sh

When: before every Bash call.

Does: reads the command from stdin JSON and blocks merging, force-pushing, pushing to main/master and branch-protection edits, even inside chains, bash -c, git -C or HEAD:master refspecs.

Result: exit 2 → the call is refused and Claude reads the reason.

PostToolUse · post-edit.sh

When: after every Edit / Write.

Does: prettier on the file. For .ts/.tsx it then runs eslint on the file and tsc --noEmit on the project.

Result: the first 40 lines of errors are sent back with exit 2 → fixed in the same turn.

Stop · stop-check.sh

When: Claude tries to end its turn (180 s timeout).

Does: finds changed + untracked src/**/*.ts(x) files, runs vitest related on them, then react-doctor on changed files.

Result: on failure, exit 2 and the turn continues. The second time (stop_hook_active) it lets the turn end in red for the human to see.

Exit codes: how a hook talks back

Exit Meaning Who sees stderr Used for
0 OK, carry on nobody clean edit, safe command
2 block / push back the model, which acts on it all three hooks, for anything the agent must fix
other non-blocking error the human only deliberately not used: the agent would carry on unaware
Show the hook wiring in .claude/settings.json 
"hooks": {
  "PreToolUse":  [{ "matcher": "Bash",
                    "hooks": [{ "type": "command", "command": ".claude/hooks/guard-bash.sh" }] }],
  "PostToolUse": [{ "matcher": "Edit|Write",
                    "hooks": [{ "type": "command", "command": ".claude/hooks/post-edit.sh" }] }],
  "Stop":        [{ "hooks": [{ "type": "command", "command": ".claude/hooks/stop-check.sh",
                               "timeout": 180 }] }]
}
Show post-edit.sh (the core of the edit loop) 
file=$(jq -r '.tool_input.file_path // empty')
npx --no-install prettier --write --ignore-unknown "$file"
case "$file" in *.ts | *.tsx) ;; *) exit 0 ;; esac
if ! out=$(npx --no-install eslint --no-warn-ignored "$file" 2>&1); then
  printf 'ESLint errors in %s:\n%s\n' "$file" "$out" | head -40 >&2; exit 2
fi
if ! out=$(npx --no-install tsc --noEmit --pretty false 2>&1); then
  printf 'Typecheck failed after editing %s:\n%s\n' "$file" "$out" | head -40 >&2; exit 2
fi

Diagram 5

Permissions + the Bash guard

Before the hook runs, permission rules in settings.json sort commands into three buckets:

deny: never allowed

  • gh pr merge
  • git push --force / -f
  • git push origin main|master
  • Edit generated generatedApi.ts
  • Edit mockServiceWorker.js

ask: human confirms first

  • npm install / i / uninstall
  • git push, gh pr create
  • Edit .github/**, CLAUDE.md
  • Edit .claude/settings.json

allow: everything else

Reading, editing source, running npm run …, tests, git on feature branches. The hooks still check every call.

Deny rules match by prefix, so cd x && gh pr merge 3 or git push origin HEAD:master would get past them. That is why guard-bash.sh exists: it takes the command apart and checks each piece.

A JavaScript copy of the rules in guard-bash.sh + permissions, for teaching. GitHub branch protection is still the real backstop.

Diagram 6

Agents, skills and rules

An agent is a model working in a loop with tools. A subagent is a separate agent with its own fresh context and a restricted tool list, used so a big search or review doesn’t fill up the main conversation. Skills are instructions loaded on demand. Rules are always-on constraints.

The agents

Agent Runs where / when Tools Job Must not
Main agent Your Claude Code session, driven by the six commands all, filtered by permissions + hooks Plan, design, spec, implement, verify, open PRs merge, push to default branch, write approved: on its own
react-reviewer Subagent, after each coherent chunk of work and before the PR Read, Grep, Glob, Bash Report bugs, performance, a11y, convention and spec-fit problems. Run react-doctor. List “unasked decisions” for the PR edit code (it reports only; the main agent fixes)
codebase-explorer Subagent, when research is needed (“where is X handled?”) Read, Grep, Glob Return a compact map: relevant files, entry points, patterns, risks implement anything; read the whole repo
@claude GitHub Action, on an issue/PR comment mentioning it (writers only) npm run, vitest, git, gh read Branch, implement, test, open a PR from an issue; answer review comments gh pr merge, gh api, force push, push to main
Autopilot GitHub Action, weekday 02:00 (off until enabled) or manual allow-listed edit, npm run, git on autopilot/* Build exactly ONE human-approved change into a PR guess answers, install deps, merge, batch changes

react-reviewer output format

src/features/items/api.ts:L23: 🟡 risk: no Zod guard on response. Add transformResponse with itemSchema.parse.
src/features/items/components/ItemForm.tsx:L41: 🔴 bug: submit stays enabled while saving. Disable on isLoading.
react-doctor: 94 (no new regressions)
Unasked decisions:
  - error toast copy "Could not save item"

🔴 bug · 🟡 risk · 🔵 nit · ❓ question. One line each, ordered by severity, each with a concrete fix. No praise, no hedging.

Skills: loaded when relevant

feature-pipeline

The master workflow: 7 steps, 2 gates, the testing standard, when to use the subagents, and guardrails. Plus claude-design.md for canvas conventions.

openspec-propose

Creates the change folder and all artifacts in one step. Planning only: it never edits code.

openspec-apply-change

Works through tasks.md. Refuses to run on approved: <pending>.

openspec-archive / sync-specs

Merges delta specs into openspec/specs/ after a merge.

openspec-explore

Thinking-partner mode: reads and discusses, never implements.

Rules: always on

  • CLAUDE.md is loaded every session: commands, gates, risk tiers, component conventions, the fixed folder layout, the state/data/forms libraries, API contract rules, PR rules and the definition of done.
  • .claude/rules/*.md are path-scoped code samples (RTK Query, Zustand, forms, MSW). They load only when a matching file is opened, which keeps the context small.
  • openspec/config.yaml sets the rules for every proposal, design and task list.
  • ESLint import boundaries enforce the architecture: lib/ imports no app layer, and components/ never imports features/.

Diagram 7

Autopilot + @claude: agents on GitHub

The same pipeline can run with nobody at the keyboard, because the gates don’t depend on anyone being present. Gate 1 already happened (a human-approved change on the default branch), and Gate 2 still happens (a PR someone reviews in the morning). When autopilot is unsure, it opens an issue instead of guessing.

Every “no” ends in something a human can act on: an issue or a draft PR. Autopilot builds UI from the design/ copy because it can’t open claude.ai.

Safety settings: concurrency: autopilot (one run at a time), an explicit --allowedTools allow-list, --disallowedTools for merge/api/force/install, pushes only to autopilot/*, and CI’s approvals job rejects any approved: line from an autopilot/* branch. On fork PRs the API key isn’t available. Never use pull_request_target with untrusted code.

Diagram 8

The /fix lane: test-first bug fixing

Qualifies only if all five are true. Otherwise the agent says which one failed and sends you to /feature:

  1. Correct behaviour is already stated in openspec/specs/ or features.md. If the spec is silent, it is a behaviour change, not a bug.
  2. No new screen, state or design change.
  3. No API contract change.
  4. No new dependency.
  5. About 100 reviewable lines or fewer.

Why RED first? A test that fails for the reason in the report proves the bug is understood. Once it passes, it guards against the bug coming back. If the agent can’t make it fail, it stops rather than guessing at a fix.

The PR says OpenSpec change: none — /fix (restores openspec/specs/<capability>), names the fixed line and the test, and stops at Gate 2. No /finish is needed.

Diagram 9

Design → code: one-way flow

Claude Design is the source of truth for the UI. The human edits there. design/ in the repo is a copy as last built, written only by /build and /sync-ui, so CI and autopilot can use it without claude.ai.

Classifying a design edit

Visual → code it after a “yes”

colour · font · size · spacing · radius · border · shadow · alignment · order · copy text · a token value

Behaviour → needs a spec + Gate 1

an input, button, link, screen or state added or removed · a changed validation rule or flow

Hex values are never copied into components. If a design would fail an axe check, the agent says so at Gate 1 or in the PR instead of shipping it.

CI + pull requests

quality job

typecheck → lint → format:check → test:coverage (floors in vitest.config.ts) → build (per-chunk bundle budget) → Playwright e2e + axe → react-doctor --scope changed.

PR size job

Counts added + deleted lines, excluding tests, mocks, openspec/, design/, e2e, lockfile and generated code. Over 400 → fail. Only a human adds the large-pr-approved label.

approvals job

Checks the diff of openspec/changes/*/tasks.md for new approved: lines and fails if a bot or an autopilot branch added them.

Safety model

Defence in depth: why the agent can’t ship on its own

No single layer is trusted. Each one catches what the layer before it missed:

1

Instructions

CLAUDE.md + skills say “never merge, never approve yourself”. This works most of the time, but it is only a prompt.

2

Permission rules

deny for merge / force / push-to-main; ask for installs, pushes, PRs, and edits to CI or CLAUDE.md.

3

PreToolUse guard

guard-bash.sh catches what prefix rules miss: chains, bash -c, refspecs, gh api.

TL;DR

The daily loop

  1. /feature <idea> → requirements, design (reused or new), spec.
  2. Edit the design on claude.ai until it looks right.
  3. /build <change> → answer the Gate 1 brief → the agent implements, and hooks, tests, react-doctor and screenshots catch problems along the way.
  4. PR opens → CI runs → a preview deploy appears.
  5. Review the PR + preview (Gate 2) → merge → /finish <change>.
  6. Changed a built screen’s design later? /sync-ui.
  7. Bug in something already shipped? /fix <bug>.

People decide at two gates; tools and the agent handle everything in between.

Teaching notes: ideas to discuss in class

Prompts vs. enforcement

Why is “never merge” written in CLAUDE.md and in a deny rule and in a hook and in branch protection? Ask students to find a command that gets past the deny list but not the hook.

Feedback speed

Why is the edit loop seconds and the review loop hours? What happens to agent quality with no typecheck hook?

Context is a budget

Subagents, path-scoped rules, /clear + notes.md for resuming: all ways to keep the main context small.

Specs as contracts

The approved: line turns “the human agreed” into a checkable fact that CI and autopilot can read.

Small PRs

400 lines is roughly what a person can review well. The agent splits work so a human can still review it properly.

Escalate, don’t loop

The 3-strike rule and “ask with a default” answer: when should an agent stop?
